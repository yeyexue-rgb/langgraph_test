# 给 AI Agent 做测试,到底难在哪?我用一个真实项目讲透了

> 多智能体系统测试集构造实战,全程干货,建议收藏。

## 开头先说个扎心的事实

现在大家都在做 AI Agent,功能演示的时候个个惊艳:"你看,它会自己调工具、自己拆任务、还能多轮对话!"

结果一上线,翻车姿势五花八门:

- 让它查时间,它把文件查询的专家叫来了;
- 明明没权限的目录,它"顺手"就去翻了;
- 你上一句问北京,它这一轮把条件串到上海的会话里了;
- 最离谱的:它**声称**自己删了个文件——其实啥也没干。

问题出在哪?**测试没跟上架构。**

单 Agent 时代,写几条用例跑一跑就够了。到了 Supervisor + 多子 Agent 的架构,路由是模型拍脑袋决定的,结果是不确定的,传统那套"输入→固定输出"的测试思路直接失效。

最近我在一篇关于「动态 Supervisor Multi-Agent 测试集构造」的方法论文章里学到了分层设计的思路,又把它完整套到了我手上一个真实项目里跑了一遍。今天就用大白话,把整个过程讲给你听。

## 一、先认识一下我们的"被测选手"

我手上这个项目,是一个面向测试工程师的 AI 助手,用 LangGraph 搭的,架构长这样:

```
用户提问
   ↓
Supervisor(总调度,自己不动手,只管派活)
   ├── 时间专家:把"明天下午3点"解析成标准时间
   ├── 文件专家:查个人空间里的文件(只读,有安全边界)
   └── SQL 专家:查测试用例库、缺陷记录
```

一句话概括:**Supervisor 是包工头,三个子 Agent 是专业工人,用户说需求,包工头决定派哪个工人干活。**

这套架构有四个让测试工程师头秃的特点:

**1. 路由靠模型"猜"。** 同样一句话,这次派给时间专家,下次可能就派错了。
**2. 参数要"传话不跑偏"。** 时间专家算出"2026-08-20",这个值要原封不动传给文件专家当筛选条件。模型最爱干的事就是顺手"美化"一下格式,一美化,全错。
**3. 多轮对话有记忆。** 你说"那本周的呢?",它得知道上一轮聊的是"报告"。但记忆要是串到别的会话里,就是事故。
**4. 有安全红线。** 文件工具只能看"个人空间"这一个目录,模型被用户一忽悠就想往外跑,必须拦住。

## 二、别急着写用例,先问自己一个问题

方法论里有个词叫**反向设计**,说白了就一句大白话:

**先想清楚你最怕什么,再决定测什么。**

我们坐下来盘了一下,最怕的事情排了个序:

1. 越界访问个人空间之外的文件——这是安全事故,一票否决;
2. 派错工人——查时间的问题派给了文件专家;
3. 传话跑偏——时间参数被模型偷偷改格式;
4. 记忆串线——A 会话的条件跑到 B 会话里。

有了这个排序,测试集的骨架就出来了。我们把用例分成六层,从零件测到整车:

| 层级 | 测什么 | 大白话解释 |
|------|--------|-----------|
| L1 | 路由决策 | 包工头会不会派错工人 |
| L2 | 参数提取 | 工人接到的任务参数对不对 |
| L3 | 多轮对话 | "那本周的呢"这种追问能不能接住 |
| L4 | 编排与异常 | 工人干砸了,包工头会不会兜底 |
| L5 | 配置变更 | 换了工人名单,系统会不会崩 |
| L6 | 端到端 | 从用户提问到最终回答的完整旅程 |

这里有个关键心得,划重点:

> **能用确定性代码测的,绝不动用大模型。**

比如时间解析的核心逻辑,我们写成了纯 Python 函数(正则匹配,不依赖任何模型)。这一层的测试跑一次不到一秒,一分钱不花,每次提交代码都能跑。这是整个测试体系里性价比最高的一环。

## 三、六层用例,一层一层怎么出题

### L1:包工头会不会派错工人

题目分三类:

**送分题**——"明天下午3点是几点?"就该派时间专家,光这一类我们就准备了 20 多种问法:"下周一上午9点""3天后""2026年8月30号"……同一个意图,问法越花哨越好。

**陷阱题**——"查一下上周改过的报告",这是复合需求:得先问时间专家"上周"是啥时候,再拿着答案去找文件专家。专门抓那种偷懒一步到位、直接丢给文件专家的乱派活。

**拒答题**——"帮我写首诗",跟工具没关系,就该直接回答,谁都不许派。模型一激动调用工具,也算错。

### L2:传话会不会跑偏

这层专门盯参数。拿文件查询举例,我们盯四种情况:

- 条件给全了的,结果对不对;
- 只说了"查报告"两个字,它会不会乱补条件;
- 啥条件都没给,它会不会瞎猜;
- 用户给了可选参数(比如"最多返回10条"),它会不会弄丢。

还有一条**硬断言**,是我们测试集里的明星用例:

时间专家吐出来的时间,必须**一个字不差**地作为筛选条件传给文件专家。我们不去看模型说了什么,而是直接从真实的工具调用记录里,把两个值抠出来对比。模型敢把 `2026-08-20T00:00:00+08:00` 改写成"8月20日"?直接判挂。

这就是我们全项目贯穿的一条铁律:**模型负责说,程序负责查,测试只信记录不信嘴。**

### L3:"那本周的呢"能不能接住

多轮对话的测试单元不是一句话,而是**一串对话**。比如:

```
第一轮:"查一下上周改过的报告" → 应该先时间后文件
第二轮:"那本周的呢?"          → 要继承"报告"这个条件,只换时间
```

我们覆盖三种剧情:

1. **后补信息**:第一轮说一半,第二轮才把目录补上;
2. **当场改口**:"不是 .txt,我要 .py";
3. **突然换话题**:聊着文件突然问"现在有几个没关闭的缺陷?",看它能不能利索地切到 SQL 专家。

还有一类**反向用例**特别重要:同时开两个会话,验证 A 会话的查询条件,打死也不能出现在 B 会话的回答里。串线就是事故。

### L4:工人干砸了怎么办

光测顺风局没用,这层专门测翻车现场:

- **工人返回一堆乱码**:系统必须降级成一个明确的错误状态,绝不能把垃圾原样递给包工头;
- **工人谎报身份**:文件专家的结果上写着"我是时间专家"?直接拒收;
- **危险操作被人工拦下**:文件查询越界时会弹出审批,我们要分别测"批准放行""改了参数再放行""直接拒绝"三条路。尤其测拒绝之后,模型必须老老实实告诉用户"这操作没执行",不许嘴硬说完成了。

### L5:换配置别把系统换崩了

架构模式切换、工具注册变更,这些都得单独测:重复注册同名工具要报错、切换架构不能复用旧会话、少了必要工具要在启动时就报错而不是跑到一半崩。

核心思想:**配置问题,死要死在门口,不能死在半路。**

## 四、题型配比:50/20/20/10

方法论给了一个很实用的配比,我们是这样落地的:

| 题型 | 占比 | 长什么样 |
|------|------|---------|
| 送分题 | ~50% | "明天下午3点""查个人空间的测试报告" |
| 超纲题 | ~20% | "帮我查下文件"(啥条件都不给)、"2月30日" |
| 陷阱题 | ~20% | "帮我看看 C 盘有啥""往上翻两级目录" |
| 红线题 | ~10% | 各种路径穿越变体、诱导它谎报操作结果 |

其中陷阱题和红线题是我们花心思最多的地方。

举个例子:拦截越界访问的判断逻辑,我们用穷举的方式喂了十种"坏路径"——`..`、`C:\Windows`、`c:\windows`(对,大小写都要测)、`/etc/passwd`、网络路径 `\\server\share`……一个都不能放过。

但只测"该拦的拦住"还不够,**同样要测"不该拦的别误伤"**:`报告/2026` 这种正常目录、名字里恰好带两个点的关键词,都绝不能被误杀。拦截器太激进,用户正常用不了,等于白做。

## 五、怎么跑:三层漏斗,把贵的留给最少的

调一次大模型,又慢又花钱。我们的执行策略像个漏斗:

**第一层:不花钱的,天天跑。** 契约校验、时间解析纯逻辑、越界判断逻辑——这些不需要模型,秒级出结果,每次提交代码自动跑。

**第二层:要花小钱的,每天跑。** 真实模型下的路由测试、参数链测试、审批全流程——打个标记,定时任务每天执行一次。

**第三层:对抗用例,重复跑。** 因为模型有随机性,陷阱题同一个输入要跑好几遍——只要有一次漏判,就算失败。用次数换置信度。

还有一个省钱小技巧:我们让 Agent 的最终回答强制走一个结构化格式(状态、回答、错误码几个固定字段)。这样一来,**很多"回答质量"的验证,变成了对几个字段的精确断言**——比拿两段文本做模糊比对靠谱多了,也便宜多了。

## 六、跑下来的几点真心话

**1. 确定性逻辑下沉,是最大杠杆。** 把时间解析、路径校验从模型里抠出来写成纯函数,测试成本断崖式下降。这一层用例,跑一万次结果都一样,安全感拉满。

**2. 别信模型的嘴,去翻它的"行车记录仪"。** 凡是模型声称干了的事,我们都去真实的工具调用轨迹里找证据。轨迹里没有,就是没干。

**3. 契约就是免费的测试。** 我们把返回格式定得很严:状态只允许几个枚举值,多一个字段都报错。格式不合法?在门口就被拒了,测试只需要验证"拒得对不对"。

**4. 安全测试要两面测。** 既要测"坏的全拦住",也要测"好的全放行"。只测一面的安全方案,大概率会在生产环境以另一种方式翻车。

**5. 测试集是活的。** 每次集成测试抓到一个新翻车姿势(比如有次模型真把时间改写成了中文格式),当场沉淀成新用例。BadCase 只踩一次,这就是回归测试的意义。

## 写在最后

给多智能体系统做测试,没有银弹,但有方法:

**分层拆掉不确定性,用程序断言代替肉眼比对,把对抗思维贯彻到每一层。**

如果你也在为 Agent 的测试发愁,不妨从这件小事开始:写下你最怕系统干的三件事,然后把每一件都变成一个可以自动判断的用例。

路,就是这么走出来的。
