**Agent 评测，测的不是「答案」，是「答案 + 过程」。**

先给你看两张我在自己机器上跑的截图（Windows + Python 3.13 + deepeval 4.2.3）：

```powershell
> pytest evals/test_agent_eval.py -m integration
evals\test_agent_eval.py ....                              [100%]
4 passed, 1 warning in 24.85s

> $env:EVAL_AGENT_MODE="subagents"; pytest evals/test_agent_eval.py -m integration
evals\test_agent_eval.py ....                              [100%]
4 passed, 1 warning in 32.40s
```

4 条用例、两种架构全绿。这篇要证明一件事：**Agent 评测不是玄学，是零基础测试工程师也能掌握的手艺。**

**为什么难测？因为「结果对」不等于「过程对」。** 一个 Agent 完全可能没查数据、靠猜给你一个正确结论——今天猜对，明天数据一变就错，你还不知道该改哪。反过来，结论错但工具调对了，说明问题在提示词、不在数据。

所以判据必须升级：**最终输出 + 工具调用轨迹，一起看。** 这是整套评测的地基。

**【图 A：一条 Agent 评测用例的四个零件】**

一条能进 CI 的用例，拆开只有四个零件：**输入**（用户怎么问）、**期望**（什么是"对"：ground truth + 该调的工具）、**证据**（它到底调了什么工具）、**判定**（通过还是失败，依据是什么）。最容易漏的是第三个——没有轨迹证据，你就退回到"只看输出"，漏掉一半的 bug。

再往下是**两层断言**：规则层（关键事实、工具路由、禁泄露，确定性、零成本）先跑；指标层（过程正确性、任务完成质量，LLM 裁判）后跑。**规则能判死的，绝不用裁判**——这是成本控制，也是准确度控制。本期 4 条用例里，有 2 条纯规则就够了。

**【图 C：实施闭环】**

动手其实就几步：装依赖 → `python scripts/seed_test_db.py` 造 ground truth → `pytest ... -m integration` 跑评测。跑通之后还有关键一步：**把分数和裁判理由留档**（`reports/eval-*.json`）。默认只看 PASS/FAIL 的评测，跑完仍是个黑盒；有了留档，失败能回溯、多次运行能比趋势，这才叫评测回归。

**【图 B：同一套用例，两种架构】**

坑我也替你踩了。四个：提示词文件是 `.md` 但加载器只认 `.txt`（评测全白跑）；`tools_called` 必须是 `ToolCall` 对象（传字符串直接报错）；指标不传 `model` 会偷偷初始化 OpenAI 裁判（报错）；工具断言写 `==` 换架构就假失败（要用 `in`）。

还有一个最阴的：多 Agent 下 SQL 用例时好时坏，报 `INVALID_SUBAGENT_RESULT`。我抓了子 Agent 的原始状态——失败时**最后是一条空 AI 消息**，模型跑完工具链忘了调结构化输出工具。**不是查询错，是模型抖动**，实测 3 次挂 2 次；加一次重试后 0/3。

**记住这句：评测失败 ≠ 产品有缺陷。** 模型抖动、评测配错、产品真错——三种情况处置方式完全不同。

## 四、长版逐图正文（10 张贴图的展开文案）

**图1（封面）**
零基础跑通第一套 Agent 评测。4 条用例、两种架构、全程可复现。核心一句话：结果对 ≠ 过程对——评测要同时看这两样。实测：single 4 passed、subagents 4 passed。

**图2（立论：结果对不代表过程对）**
传统接口测试只看"返回对不对"，放到 Agent 上会漏掉一半 bug。结论对、过程错 = 它是猜的，数据一变就错；结论错、过程对 = 工具调对了、总结错了。所以判据要变：从"返回对不对"改成"最终输出 + 工具调用轨迹一起看"。这一条，是整套评测的地基。

**图3（一条用例 = 四个零件）**
①输入（用户怎么问）；②期望（ground truth + 该调的工具）；③证据（轨迹 tools_used）；④判定（通过/失败，依据）。最容易漏的是 ③——没有轨迹证据，就只能退回"只看输出"，漏掉"结果对、过程错"。

**图4（可复现三件事）**
跑一次不算评测，能重复才算。①ground truth 有出处（种子数据 P0=3/blocker=2）；②每条用例独立 thread_id，否则第二条带着第一条记忆、结果被污染；③证据回传，评测端才判得了过程。

**图5（两层断言）**
规则能判死的，绝不用裁判。规则层：确定性、零成本、先跑（关键事实/工具路由/禁泄露）；指标层：LLM 裁判、有成本、后跑（相关性、完成质量）。本期 4 条用例：2 条用指标、2 条纯规则。省的不是钱，是被裁判噪声带偏的概率。

**图6（动手两条命令）**
装依赖 → `pip install -r requirements.txt` + `pip install -U deepeval` → 造数据 `python scripts/seed_test_db.py` → 跑：`pytest evals/test_agent_eval.py -m integration`（单 Agent）/ 加 `EVAL_AGENT_MODE=subagents`（多 Agent）。标记 `-m integration` 是为了分层执行：PR 跑规则、夜间跑全量。

**图7（实证①单 Agent）**
Windows · Python 3.13 · deepeval 4.2.3：`4 passed, 1 warning in 24.85s`。4 条用例：SQL 数量（=3）、时间解析（15:00）、天气越界不编造、注入不泄露。指标：过程正确 1.0、完成度 1.0、平均 1.000。

**图8（实证②多 Agent）**
`$env:EVAL_AGENT_MODE="subagents"` 后：`4 passed in 32.40s`。同一套用例、换架构仍全绿。差别在工具链：single 是 `[parse_natural_datetime]`，subagents 是 `[time_specialist, parse_natural_datetime]`——多出来的是主管层包装工具。所以工具断言要用"包含"，不能用"相等"。

**图9（四个坑）**
①提示词被忽略（加载器只认 .txt，提示词是 .md → 评测全白跑）；②类型不对（tools_called 要是 ToolCall 对象）；③裁判偷偷走 OpenAI（不传 model 就报错）；④断言绑死架构（== 换架构假失败 → 改 in）。共同点：都不是产品错了，是评测配错了。

**图10（隐藏缺陷 + 留档 + CTA）**
最阴的一条：多 Agent 下 SQL 用例时好时坏。抓状态后发现失败时最后是空 AI 消息——模型忘了调结构化输出工具。结论：模型抖动，加一次重试，2/3 失败 → 0/3。再补一刀：把分数和裁判理由留档成 JSON，失败能回溯、多次运行能比趋势。完整源码：后台回复「agent」。
