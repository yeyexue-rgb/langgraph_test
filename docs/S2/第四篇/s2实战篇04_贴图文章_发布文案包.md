【贴图 1】

我们已经攒齐三样东西：**评测**（过没过）、**追踪**（发生了什么）、**监控**（有没有在变坏）。

但真实情况往往是——**三个工具都在跑，团队还是乱**：评测报告一堆但红灯照发；出了问题不知道先看哪个；夜里评测没人看；分数从 0.95 悄悄掉到 0.82，没人发现。

**问题不在工具，在流程。**

【贴图 2】【贴图 3】

**第一步：分清三层职责。**

| 层 | 工具 | 回答 | 何时跑 |
|---|---|---|---|
| 质量网关 | DeepEval + 门禁 | 能不能**放行**？ | PR / 每晚 / 发版前 |
| 现场取证 | Langfuse | 这次**为什么**这样？ | 出问题时随时 |
| 长期趋势 | 监控看板 | 是不是在**变坏**？ | 7×24 |

三层是**漏斗**：线上流量 →（追踪）筛出异常 →（评测）固化成用例 →（门禁）挡住会让分数下降的改动。**顺序不能乱**——没有追踪，用例只能拍脑袋造；没有门禁，评测就只是报告。

【贴图 4】

**流水线五个节点：** ① 本地提交跑规则层（零成本秒级）→ ② PR 门禁（规则不可退让 + 关键用例）→ ③ 合并后夜间全量评测 + 门禁判定 → ④ 发版前关键集 + 人工复核 → ⑤ 线上追踪采样 + 异常回流。

一条铁律：**越靠近提交越要便宜，越靠近上线越要全面。**

【贴图 5】

为什么必须分层？因为**成本曲线**：规则断言 0 成本毫秒级；结构断言极低秒级；LLM 裁判有成本、分钟级。**分层不是为了好看，是为了让"每次都跑"在经济上成立。**

【贴图 6】

**第二步：把门禁写进 CI。** 留档 JSON 是给人看的，门禁是给机器判的：

```bash
python scripts/quality_gate.py reports/eval-single-*.json \
    --min-metrics-pass-rate 0.95 --min-avg-score 0.80 \
    --baseline 昨天.json --max-avg-drop 0.05
```

四条判定任一不满足就红。真实输出（放行 / 拦截）：

```
| 架构 | 用例 | 指标通过 | 平均分 | 不通过用例 |
| single | 4 | 4/4 (100%) | 1.0  | 无 |
结论：✅ 放行
---
| single | 4 | 3/4 (75%) | 0.8875 | SQL · P0 用例数量 |
结论：❌ 不予放行
  - 指标通过率 75.0% < 要求 95.0%
  - 平均分较基线下降 0.113 > 允许 0.050
```

【贴图 7】

**注意第三条判定：对比基线。** 最阴的情况是——**一次改动把所有用例从 0.95 拉到 0.82，但一条都没跌破阈值**。只看红绿灯你完全发现不了；看"是否比基线退化"立刻拦住。**上一期的留档，是这一期的弹药。**

【贴图 8】

**第三步：出问题的分诊顺序**（这是最实用的一节）：

| 报信人 | 先看 | 再看 |
|---|---|---|
| PR 门禁红了 | 评测 | 追踪 |
| 线上监控告警 | 追踪 | 评测 |
| 用户说答得不对 | 追踪 | 固化成用例 |
| 用户说太慢了 | 追踪（耗时归因） | 监控 |

**每次线上问题的终点，都应该是一条新的评测用例。** 这样评测集才是"你系统真实踩过的坑的集合"。

【贴图 9】

**四个坑：** ① 门禁太慢没人等（裁判别塞进 PR）；② 阈值拍脑袋（先用历史分布）；③ 只看通过率不看分数趋势；④ 告警没有归属（没人认领 = 噪音）。

【贴图 10】

**最后浓缩成三句话：** ① 提交时，便宜的先拦；② 夜里，贵的全跑 + 门禁判定 + 基线对比；③ 出事后，追踪取证 → 定位 → **固化成用例** → 门禁守住它。

做到第三条，你就不再是每次救火的人，而是**让火越来越难烧起来**的那个人。

## 四、长版逐图正文（10 张漫画贴图）

**贴图1（封面）** 质量流水线：评测 · 追踪 · 监控。工具都齐了，为什么还是乱？网关、取证、趋势三层职责，顺序对了乱就消失。

**贴图2（工具齐了还是乱）** 你可能每天都在经历：评测报告一堆但红灯照发；出问题不知先看哪个；夜里评测没人看；分数慢慢掉没人发现。问题不在工具，在流程——工具解决"能不能看见"，流程解决"看见了怎么办"。

**贴图3（三层职责）** ① 质量网关（DeepEval）：能不能放行，PR/每晚/发版前；② 现场取证（Langfuse）：这次为什么这样，出问题时随时查；③ 长期趋势（监控）：是不是在慢慢变坏，7×24。三层是漏斗不是并列，顺序乱了工具就白买。

**贴图4（流水线全景）** ① 本地提交跑规则层 → ② PR 门禁 → ③ 合并后夜间全量 + 门禁判定 → ④ 发版前关键集 + 人工复核 → ⑤ 线上采样 + 异常回流。铁律：越靠近提交越便宜，越靠近上线越全面。

**贴图5（为什么必须分层）** 不是好看，是为了跑得起。规则断言 0 成本毫秒级、结构断言极低秒级、LLM 裁判有成本分钟级。能用规则判死的，绝不上裁判——这就是分层的全部理由。

**贴图6（把门禁写进 CI）** 四条判定：指标通过率、平均分、不得比基线明显下降、不通过用例数。留档是给人看的，门禁是给机器判的。CI 里 PR 跑规则层、夜里跑全量，判定不过直接拦住。

**贴图7（最阴的情况）** "全都过了！然后呢？" 分数从 0.95 悄悄掉到 0.82，但没一条跌破阈值——只看红绿灯发现不了。必须对比基线：平均分下降 0.113 ＞ 允许 0.050 → 门禁拦下。上一期的留档，是这一期的弹药。

**贴图8（出问题先看哪个）** 门禁红了先看评测再看追踪；监控告警先看追踪再看评测；用户说答得不对先看追踪再固化成用例；用户说太慢先看追踪再看监控。每次线上问题的终点是一条新的评测用例。不靠感觉，靠顺序。

**贴图9（四个坑）** 门禁太慢（PR 等十分钟 → 开发直接关掉）；阈值拍脑袋（凭啥 0.8？用历史分布定）；只看通过率（4/4 通过 ≠ 没问题）；告警没归属（发群里没人认领 = 噪音）。门禁要有人认领，不然第二天自己就绿了。

**贴图10（写在最后）** 三句话：提交时便宜的先拦；夜里贵的全跑 + 门禁判定；出事后取证 → 固化成用例。做到第三条，你不再是每次救火的人，而是让火越来越难烧起来的人。
