# 质量流水线：评测、追踪、监控怎么串起来

> Agent 测试进阶实战（第二季）· 实战篇 04
> 配套源码：https://github.com/yeyexue-rgb/langgraph_test

---

## 引子：工具都齐了，为什么还是乱？

回顾一下我们已经攒齐的三样东西：

- **评测**（DeepEval）：告诉这次**过没过**；
- **追踪**（Langfuse）：告诉这次**发生了什么**；
- **监控**：告诉**线上有没有在变坏**。

按理说够了。但真实情况往往是——**三个工具都在跑，团队还是乱。**

- 评测报告生成了一堆，**红灯了照发**，因为"没时间看"；
- 出了问题，先看评测？先看追踪？先看监控？**谁都不知道顺序**；
- 夜里的评测没人看，早上开会才想起；有告警但**没人认领**；
- 分数从 0.95 慢慢掉到 0.82，**没有一个人发现**。

**问题不在工具，在流程。** 这篇文章就讲一件事：**把这三样串成一条流水线，并且明确"出问题先看哪个"。**

---

## 一、先分清三层职责（别让一个工具干三个的活）

| 层 | 工具 | 回答的问题 | 什么时候跑 | 谁看 |
|---|---|---|---|---|
| **质量网关** | DeepEval + 门禁 | 能不能**放行**？ | 每次 PR / 每晚 / 发版前 | 研发 + 测试 |
| **现场取证** | Langfuse | 这次**为什么**这样？ | 出问题时**随时** | 测试 + 研发 |
| **长期趋势** | 监控 / 指标看板 | 是不是在**慢慢变坏**？ | 7×24 | 测试 + 值班 |

三层的关系是**漏斗**：

```
线上全部流量
   ↓ 追踪：全都记下来（采样）
筛出异常 / 低分
   ↓ 评测：把异常固化成用例
每次提交都拦
   ↓ 门禁：挡住会让分数下降的改动
```

**顺序不能乱。** 很多团队一上来就想要"全自动评测门禁"，但没有追踪，你的用例只能拍脑袋造；没有门禁，你的评测就只是报告。

---

## 二、流水线全景：五个节点

```
① 本地提交     → 跑规则层（零成本、秒级）
② PR 门禁      → 规则层不可退让；关键用例集（抽样指标）
③ 合并后       → 夜间全量评测 + 门禁判定 + 留档
④ 发版前       → 关键用例集 + 人工复核低分项
⑤ 线上         → 追踪采样 + 指标看板；异常 case 回流评测集
```

一条铁律：**越靠近提交，越要便宜；越靠近上线，越要全面。**

原因是**成本曲线**——同样一条用例：

| 层 | 单次成本 | 耗时 | 能跑多少 |
|---|---|---|---|
| 规则断言 | 0（不调模型） | 毫秒 | 全量，每次提交 |
| 结构/路由断言 | 极低 | 秒级 | 全量，每个 PR |
| LLM 裁判指标 | 有成本（token） | 秒~分钟 | 抽样；夜间全量 |

**所以分层不是为了好看，是为了让"每次都跑"这件事在经济上成立。**

## 三、实战：把门禁写进 CI

光有"留档 JSON"不够——**留档是给人看的，门禁是给机器判的。** 我们新增一个 `scripts/quality_gate.py`：

```bash
python scripts/quality_gate.py reports/eval-single-*.json \
    --min-metrics-pass-rate 0.95 \
    --min-avg-score 0.80 \
    --baseline reports/eval-single-昨天.json \
    --max-avg-drop 0.05 \
    --summary qa-summary.md
```

它做四件事，**任一不满足就退出码 1（CI 红）**：

1. 指标通过率 ≥ 阈值；
2. 平均分 ≥ 阈值；
3. 相比基线，**平均分下降不超过阈值**（← 这条最关键，见下）；
4. 不通过用例数 ≤ 允许值。

真实输出（正常留档，放行）：

```
| 架构 | 用例 | 指标通过 | 平均分 | 最低分项 | 不通过用例 |
| single | 4 | 4/4 (100%) | 1.0 | ToolCorrectnessMetric 1.0 | 无 |

结论：✅ 放行（所有阈值满足）
```

造一份"分数退化"的留档，门禁立刻拦下：

```
| 架构 | 用例 | 指标通过 | 平均分 | 最低分项 | 不通过用例 |
| single | 4 | 3/4 (75%) | 0.8875 | TaskCompletionMetric 0.55 | SQL · P0 用例数量（期望 3） |

结论：❌ 不予放行
  - 指标通过率 75.0% < 要求 95.0%
  - 不通过用例 1 条 > 允许 0 条：SQL · P0 用例数量（期望 3）
  - 平均分较基线下降 0.113 > 允许 0.050（基线 1.000 → 本次 0.887）
```

**注意第三条。** 很多团队的门禁只判"通过/失败"——那会漏掉最阴的情况：

> **一次改动把所有用例的分数从 0.95 拉到 0.82，但一条都没跌破阈值。**
> 只看红绿灯，你完全不会发现；看"对比基线是否退化"，立刻拦住。

这就是**为什么一定要留档 + 基线对比**。上一期留下的 JSON，在这一期变成了门禁的弹药。

CI 侧对应一份三层工作流（`.github/workflows/quality.yml`）：

```yaml
rules:                     # 每个 PR：不调模型，秒级
  run: pytest tests -q -m "not integration"

evals:                     # 夜间/手动：真模型 + 裁判
  if: github.event_name != 'pull_request'
  run: |
    python scripts/seed_test_db.py
    pytest evals/test_agent_eval.py -m integration -q
    EVAL_AGENT_MODE=subagents pytest evals/test_agent_eval.py -m integration -q

  # 门禁判定 + 摘要进 Actions 概览 + 留档上传 artifact
```

## 四、出问题了，先看哪个？（分诊决策树）

这是本文最实用的一节。**"先看哪个"有固定顺序，不该靠感觉。**

**第一步：问"哪一层报的？"**

| 报信人 | 先看 | 再看 |
|---|---|---|
| PR 门禁红了 | **评测**（哪个用例、哪个指标掉了） | 追踪（这条用例的完整链路） |
| 线上监控告警 | **追踪**（采样到的坏 case） | 评测（能否复现 → 变成用例） |
| 用户投诉"答得不对" | **追踪**（拿真实请求回放） | 评测（把它固化成用例） |
| 用户投诉"太慢了" | **追踪**（耗时归因：模型 or 工具） | 监控（是不是普遍劣化） |

**第二步：判断"是真的坏了还是抖了"。**
（这就是实战篇 02 那套三角定位法：看证据 → 看复现 → 看维度。）

**第三步：决定"修完怎么防它再犯"。**
- 逻辑缺陷 → 提 bug + **补一条评测用例**（防止回归）；
- 抖动 → 容错 + 把**重试率做成指标**；
- 假阴性 → 修断言。

**关键认知：每一次线上问题的终点，都应该是一条新的评测用例。**

```
线上问题 → 追踪取证 → 定位 → 修复 → 固化成用例 → 门禁从此守住它
```

跑完这一圈，"评测集"才不是拍脑袋造的，而是**你的系统真实踩过的坑的集合**。

## 五、四个坑

**坑 1：门禁太慢，没人等。**
把 LLM 裁判塞进 PR 门禁，每个 PR 等 10 分钟 → 开发直接关掉它。
**修法**：PR 只跑规则层 + 少量关键用例；全量留给夜间。

**坑 2：阈值拍脑袋。**
"平均分 0.8 吧"——凭什么？0.8 是你能接受的下限吗？
**修法**：先用历史留档跑统计（近 20 次分布），再定阈值；并且**用基线对比兜底**。

**坑 3：只看通过率，不看分数趋势。**
4/4 通过 ≠ 没问题（可能全都是勉强 0.71 过的）。
**修法**：门禁必须同时看**平均分**和**相对基线的变化**。

**坑 4：告警没有归属。**
"评测红了"发到群里，没人认领，第二天自然绿了（因为没人管）。
**修法**：每条门禁规则写清**谁负责**（哪条用例对应哪个模块/谁修的），否则告警就是噪音。

## 六、写在最后

回到开头的问题：工具都齐了，为什么还是乱？

因为**工具解决"能不能看见"，流程解决"看见了怎么办"。**

这条流水线的价值，最后浓缩成三句话：

1. **提交时**：便宜的先拦（规则层，秒级，不可退让）；
2. **夜里**：贵的全跑（指标层 + 门禁判定 + 留档 + 基线对比）；
3. **出事后**：追踪取证 → 定位 → **固化成用例** → 门禁守住它。

做到第三条，你就不再是"每次都在救火"的测试工程师，而是**让火越来越难烧起来**的那个人。
