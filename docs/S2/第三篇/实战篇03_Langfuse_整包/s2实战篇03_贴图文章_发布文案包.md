## 二、摘要（120 字内）

评测回答"过没过"，追踪回答"发生了什么"。这篇把 Langfuse 接进多 Agent 项目：新增一个可观测性模块、运行配置挂回调（业务代码一行没改）、thread_id 映射成会话，没配 key 就是 no-op。附三个马上能用的场景：慢在哪、错在哪一步、badcase 回灌评测集。

【贴图 1】

上一期聊了"评测红了到底谁错了"。这一期往前推一步：**当评测只给你"通过/失败"两个字，你怎么知道过程里发生了什么？**

评测和追踪，回答的是两个不同的问题：

| | 评测（DeepEval） | 追踪（Langfuse） |
|---|---|---|
| 回答 | 这次**过没过**？ | 这次**发生了什么**？慢在哪、错在哪步？ |
| 输出 | 分数 / 通过率 | 完整调用树：谁调了谁、耗时、token |
| 覆盖 | 你写了的用例 | 线上**全部**真实流量 |
| 成本 | 每条都要钱（裁判） | 可采样，能压很低 |

一句话：**评测是守门员，追踪是行车记录仪。** 守门员只守你安排他守的那几脚球；行车记录仪是你出事后唯一能回看现场的东西。

【贴图 2】

**三个概念先弄明白：**

- **Trace（一次会话）**：你问一句、它答一句，整条链路算一条；
- **Span（一次运行步骤）**：Trace 内部的节点，`supervisor → sql_specialist → sql_db_query` 层层嵌套，构成调用树；
- **Generation（一次模型调用）**：额外记录 token、成本、模型名、完整 prompt 与输出。

**Span 树就是 Agent 的"行车轨迹"。**

【贴图 3】【贴图 4】

**接入三步，业务代码一行不改：**

```bash
pip install -r requirements-observability.txt   # langfuse>=4.0.0
# .env 配 LANGFUSE_PUBLIC_KEY / SECRET_KEY / HOST
```

① 新增 `agent_core/observability.py`——管开关、采样、脱敏、回调；
② 在 `AgentService` 里挂回调，就一行：

```python
config = self._attach_tracing(
    self._build_config(thread_id), thread_id=thread_id, context=context,
)
```

③ 把 `thread_id` 映射成 Langfuse 的 session、`user_id` 映射成 user、架构模式做成 tag：

```python
"metadata": {"langfuse_session_id": thread_id, "langfuse_user_id": user_id,
             "langfuse_tags": ["agent", f"mode:{agent_mode}"]}
```

**为什么要映射？** 这样你就能在平台上按"架构模式"筛选，直接对比 single 与 subagents 的耗时分布——比评测用例给你的信息量大得多。

【贴图 5】

关键设计：**没配 key 就是 no-op。** 未启用时连回调对象都不创建，彻底零开销，行为与改造前逐字节一致——这条被回归测试守着（`pytest tests -m "not integration"` → **176 passed**）。

【贴图 6】

**打开黑匣子能看到什么？** 配好 key 再跑一次，平台上出现一棵树：

```
session: eval-8f3c   [mode:subagents]
└── agent-subagents                    11.2s
    ├── supervisor                      3.1s  2,148 tokens
    │   └── sql_specialist              6.8s
    │       ├── sql_db_list_tables      0.3s
    │       ├── sql_db_schema           0.4s
    │       ├── sql_db_query_checker    2.1s  ← LLM
    │       └── sql_db_query            0.2s  → [(3,)]
    └── 结构化输出                       0.6s
```

第一次看到这棵树我有点震撼：**一次"查询"背后这么多步，而 87% 的时间花在模型调用上，SQL 查询只占 0.2 秒。**

【贴图 7】

**场景一：慢在哪。** 以前用户说"你这个 Agent 好慢"，你只能猜；现在能直接回答：**87% 时间在两次模型调用**。于是优化方向明确了——能不能省掉 query_checker、能不能换更小的模型，而不是盲目去优化数据库。

**场景二：错在哪一步。** 两条轨迹摆一起对比，差异点在第 3 步：正常轨迹调了 `sql_db_query` 拿到 `[(3,)]`，异常轨迹**跳过查询直接作答**，于是编造答案。评测只会说"这条没过"，追踪会说"它在哪抄了近道"。

【贴图 8】【贴图 9】

**场景三：把线上 badcase 回灌成评测用例（闭环）。**

```
线上真实流量 → 追踪记录 → 筛出烂 case → 复现成评测用例 → 进评测集
```

**评测集不该拍脑袋造，应该从真实轨迹里"长"出来。** 跑一周追踪筛出 20 条烂 case，胜过闭门造 200 条。

【贴图 10】

**四个坑：** ① 忘 flush（脚本跑完就退出 → 平台空白）；② 采样太狠（想复盘的坏 case 被采样掉）；③ 密钥进平台（prompt 带 key/手机号就是泄露）；④ 以为不追踪不消耗（回调本身有开销，所以我们把 `should_trace()` 放在最前面）。

**贴图2（两个问题）** 评测问"过没过"，追踪问"发生了什么"。只评测 → 漏掉没写用例的场景；只追踪 → 没有"通过线"。两个都要：评测守住底线，追踪看见真相。

**贴图4（接入三步）** ① 装依赖 + 配 key；② 加一个 observability 模块（管开关/采样/脱敏/回调，业务代码一行不改）；③ 把回调挂到运行配置，就这么一行。未启用则原样返回，零开销。

**贴图6（打开黑匣子）** 完整调用树：agent-subagents 11.2s → supervisor 3.1s → sql_specialist 6.8s → 四个工具。第一次看到会震撼：一次"查询"背后这么多步；模型思考 5.2s ≫ 查数据 0.2s。事实和直觉常常相反。

**贴图7（慢在哪）** 用户说"你这 Agent 好慢"——以前只能猜，现在能给出 87% 在模型调用。优化方向立刻明确：省掉 query_checker？换更小的模型？而不是盲目优化数据库。

**贴图8（错在哪一步）** 两条轨迹对比：正常轨迹第 3 步 `sql_db_query` → [(3,)]；异常轨迹第 3 步直接作答 → 编造答案。评测说"没过"，追踪说"它在哪抄了近道"。上次那个偶发缺陷，有追踪两分钟搞定。

**贴图9（闭环）** 线上流量 → 追踪记录 → 筛烂 case → 复现成评测用例 → 进评测集。评测集不该拍脑袋造，应该从真实轨迹里"长"出来。跑一周筛 20 条，胜过闭门造 200 条。
