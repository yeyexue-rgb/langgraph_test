# 评测红了，到底是评测错了还是产品错了？

> Agent 测试进阶实战（第二季）· 实战篇 02
> 案例来自直连仓库：https://github.com/yeyexue-rgb/langgraph_test（完整源码见文末）

---

## 一个每个测试工程师都会撞上的两难

深夜，CI 红了。

你面前有一条失败的用例，只有一个冷冰冰的错误码。你有 30 秒决定：

- **是提 bug 给开发**（"你们 Agent 有缺陷"）
- **还是改自己的评测**（"我断言写错了"）

赌错了的代价是双向的：

| 你的判断 | 如果判断错了 | 后果 |
|---|---|---|
| 「这是缺陷」 | 其实是评测问题 | 开发被你骚扰三次后，**再也不信你的红色** |
| 「这是评测问题」 | 其实是真缺陷 | **缺陷漏到线上**，你背锅 |

这就是「**假阴性**」的可怕之处——评测系统自己骗了自己，你却在报告上盖了绿色的章。

这篇要讲的，是它最典型的兄弟问题：**评测报错时，怎么判断错的是评测，还是产品？** 我会用我自己踩的一个案例，把判断过程一步步摊开给你看。

结论先给你：**大多数时候，答案不在"信谁"，而在于你有没有把"证据"留在手上。**

---

## 一、先把「红」分成三种，而不是一种

测试老手和新手的区别，往往就在这一步：新手看到"红"只有一种反应——修东西。老手会先分诊：

| 类型 | 本质 | 特征 | 处置 |
|---|---|---|---|
| **① 逻辑缺陷** | 产品真的错了 | **稳定复现**，证据指向代码逻辑 | 提 bug，修产品 |
| **② 假阴性** | 评测系统自己错了 | 产品行为其实正确，是断言/配置/类型写错 | 修评测，别动产品 |
| **③ 抖动型不稳定** | 概率性的"时好时坏" | **不可稳定复现**，同一输入结果不同 | 两条腿：容错 + 可观测 |

**关键认知：这三种的处置方式完全相反。**

①要把产品改对，②要把评测改对，③既不能只改产品、也不能只改评测——你要**降低它的概率，同时把它变成一个能被监控的数字**。

难点在于：**它们长得一模一样。** 一条失败的用例，不会自带"我是哪种"的标签。所以你需要一套方法去逼问它。

## 二、三角定位法：用三个问题逼出真相

我给这套方法起了个名字——**三角定位**。三个角度交叉，指向同一个答案时才下结论。

**【图 A：三种「红」的分诊决策树】**

**第一问：证据链完整吗？（看现场）**
不要看错误码，去看**原始状态**。错误码是产品给你的"结论"，而你要的是"现场"。
在我们的项目里，错误码是 `INVALID_SUBAGENT_RESULT`。光看它，你只能猜；但我把子 Agent 的**原始 state** 打出来之后，答案基本就自己浮出来了（后面细说）。

**第二问：能稳定复现吗？（做最小复现）**
把用例缩到最小——去掉评测框架、去掉指标、直接调用那一个模块，连跑 3 次。
- 稳定失败 → 大概率是 ① 逻辑缺陷
- 时好时坏 → 大概率是 ③ 抖动
- 稳定通过 → 你要怀疑 ② 假阴性了（评测本体的问题）

**第三问：换个维度也错吗？（交叉验证）**
同一个能力，用不同方式测两遍：
- 规则断言（确定性）说它错，指标（LLM 裁判）也说它错 → 更可能是 ①
- 规则说错、指标说对（或反过来）→ 先怀疑 ②（断言写错/类型错/裁判没配）

三个问题走完，答案基本收敛。**下面是我这次的真实过程。**

## 三、案例实录：从「疑似数据库故障」到「模型抖动」

### 3.1 现象

多 Agent（Supervisor 架构）模式下跑评测，SQL 那条用例**时好时坏**：

```
E  AssertionError: assert '3' in
   '无法查询 P0 优先级测试用例数量，数据库查询子专家返回了无效结果
    （错误代码：INVALID_SUBAGENT_RESULT）。'
```

而**单 Agent 模式下，同一条用例 5 次全绿**。

### 3.2 第一反应（错的）

"数据库连不上了？子专家权限不够？SQL 写错了？"

——**这就是新手最容易掉进去的坑**：看到"数据库查询失败"就去查数据库。

我用三角定位的**第三问**一秒排除了它：**单 Agent 模式全绿**。同一个数据库、同一条 SQL、同一个种子数据——如果数据库真有问题，单 Agent 也该错。**错不在数据层。**

### 3.3 缩小范围（第二问：最小复现）

我绕开评测框架，单独把这个 SQL 子 Agent 建出来，直接调用，连跑 3 次：

```
第1次: status=error  error_code=INVALID_SUBAGENT_RESULT
第2次: status=error  error_code=INVALID_SUBAGENT_RESULT
第3次: status=success
```

**2/3 失败。** 结论很清楚了：

- 不是"稳定失败" → 排除纯逻辑缺陷（①）
- 不是"稳定通过" → 排除假阴性（②）

**它是 ③ 抖动型不稳定。** 但先别急着贴标签——我还需要知道**"抖"在哪个环节**，否则没法处置。

### 3.4 抓现场（第一问：证据链）

这是整个排查最关键的一步。我在子 Agent 外面挂了探针，失败时把**原始 state 的最后几条消息**打出来：

```
失败时（structured_response 缺失）：
 - AIMessage | (空内容) | tool_calls= ['sql_db_query_checker']
 - ToolMessage | SELECT COUNT(*) AS p0_count FROM test_cases WHERE priority = 'P0'
 - AIMessage | (空内容) | tool_calls= ['sql_db_query']
 - ToolMessage | [(3,)]
 - AIMessage | (空内容) | tool_calls= None      ← 就是它！

成功时：
 - ...
 - AIMessage | (空内容) | tool_calls= ['SubagentResult']   ← 正常应该调这个
```

看出来了吗？

**失败时，最后一条是一条"空 AI 消息"，`tool_calls` 是 `None`。**

这意味着：模型老老实实查完了数据（`[(3,)]` 就在那里，数据是对的！），**但它忘了调用"结构化输出"工具 `SubagentResult` 就结束了对话**。

而子 Agent 的输出是被强类型约束的——它必须吐一个结构化的 `SubagentResult`，主管才接得住。没吐，主管只能回一句"子专家返回了无效结果"。

**所以真相是：数据没错、SQL 没错、评测也没错。是模型在"收尾"这一步，偶发性地漏了一个动作。**

### 3.5 定性：这不是假阴性，是「抖动型缺陷」

这里有一个非常重要、也非常容易被搞混的判断：

> **错误码难看 ≠ 评测错了；偶发 ≠ 假阴性。**

- 评测报的 `INVALID_SUBAGENT_RESULT` 是**真实的**——子 Agent 确实没返回有效结果，评测如实记录，**它没撒谎**；
- 这不是 ② 假阴性，而是**被测系统在特定架构下的真实不稳定**：多 Agent 每多一层"交接"，就多一次"交接失败"的机会；
- 也不属于 ① 纯逻辑缺陷——因为没有哪一行代码写错了，它是**概率问题**，不是**逻辑问题**。

**④ 定义**：抖动型缺陷 = 系统行为正确率 < 100%，但在相同输入下不可稳定复现的可靠性问题。

这类问题的可怕之处在于：**它会伪装成"偶发失败"被忽略**。开发一句"重跑就好了"，就把一个 33% 失败率的问题盖过去了。

## 四、怎么区分假阴性 vs 真缺陷：一张判据表

把上面的方法论固化成表，你下次直接套：

| 观察到的现象 | 更可能是 | 下一步动作 |
|---|---|---|
| 错误码难懂，但原始状态里**数据/结果是对的** | ③ 抖动 or ② 假阴性 | 抓原始状态，看"最后一步动作"是否缺失 |
| **稳定复现**，且证据指向某个具体逻辑分支 | ① 真缺陷 | 提 bug，附最小复现 |
| 单架构全绿、多架构才挂（或反之） | ③ 架构相关的抖动 | 单独复现子模块，定位"交接点" |
| 断言过不去，但**人工看输出明明是对的** | ② 假阴性（断言太严/类型错） | 检查断言写法、类型、阈值 |
| 换了断言方式（规则↔指标）结论就反转 | ② 假阴性（断言不可靠） | 用规则断言做主判据 |
| 提示词/配置"改了像没改" | ② 假阴性（配置没生效） | 先验证配置生效，再谈评测 |
| 只在特定机器/时段失败 | ③ 环境抖动 | 排查并发、超时、额度、网络 |

**【图 B：一次假阴性排查的现场证据】**

再送你一句判据口诀：

> **看证据（现场对不对）→ 看复现（稳不稳）→ 看维度（交叉验证一致吗）。**
> 三问下来还犹豫，说明你的证据不够，不是结论不够。

顺便说一个**典型假阴性**作为对照——就在同一个项目里，我遇到过一次更隐蔽的：

> 项目提示词放在 `prompts/*.md`，但加载器只认 `.txt`。结果：**Agent 根本没吃到系统提示词**，但评测**照样全绿**。
> ——评测"通过了"，结论却是假的。**这就是假阴性**：产品行为其实不达标，是评测自己瞎了。
> 修法：让加载器 `.md` 优先、兼容 `.txt`。

一个案例：**同项目里的"真缺陷 + 真抖动"**；一个对照：**同项目里的"假阴性"**。你看，区分它们的，从来不是"红不红"，而是**证据链**。

## 五、处置：重试是不是"掩盖问题"？

定位到是抖动后，我给子 Agent 加了一次重试，实测 **2/3 失败 → 0/3**。

这时一定会有人问——**"重试是不是在掩盖问题？"**

问得好。答案是：**取决于你有没有把重试"看见"。**

**裸重试 = 掩盖**（把失败吞掉，指标一片绿，你永远不知道系统有多不稳）。
**可观测重试 = 治理**（把重试次数打出来，它变成了一个新的质量信号）。

所以正确的做法是两条腿：

**腿一：容错（把概率降下来）**
- 对"模型没吐结构化结果"这类**终态可判**的失败，重试一次（别无限重试）；
- 重试要有上限、要有超时，且**只能重试幂等/只读操作**——写操作重试要先想清楚副作用。

**腿二：可观测（把概率暴露出来）**
- 记录**重试率**、**首次成功率**；
- 把"重试率"当成一个正式的质量指标，进监控、进趋势图；
- **首次成功率**才是系统真实的稳定性——重试只是兜底，不是成绩。

我在评测留档里加了这段，就是为了让"抖动"无处藏身：

```python
for _ in range(2):                       # 上限 2 次，不做无限重试
    state = sql_agent.invoke(payload)
    result = serialize_subagent_result(state, ...)
    if parsed.get("error_code") != "INVALID_SUBAGENT_RESULT":
        return result                    # 成功即返回
# 两次都失败 → 如实上报，不吞
```

**【图 C：抖动治理 = 容错 + 可观测】**

一句话总结这一节：

> **抖动的正确处置，不是"让它不失败"，而是"让它失败得看得见"。**

## 六、可抄的排查清单（7 步）

下次你的 Agent 评测红了，按这个顺序走，不要跳步：

1. **别急着提 bug，也别急着改断言**——先分诊：逻辑缺陷 / 假阴性 / 抖动；
2. **打出原始状态**（不是错误码）：消息列表、工具调用、结构化输出，一个都别漏；
3. **找"最后一步动作"**：Agent 流水线里，失败常常发生在"收尾"（交接、结构化输出、总结）；
4. **做最小复现**：绕开框架，单独调那个模块，**连跑 3 次**（1 次不算数）；
5. **交叉验证**：换一种断言方式（规则↔指标）看结论是否反转；
6. **先验证配置生效**：提示词、阈值、裁判模型有没有真的加载（防假阴性）；
7. **处置要"容错 + 可观测"**：能给重试就给上限重试，同时把重试率/首次成功率做成指标。

## 七、写在最后

回到开头那个两难：评测红了，你信谁？

我的答案是——**别信"谁"，信"证据"**。

- 想提 bug？先交出**原始状态 + 最小复现**；
- 想改断言？先证明**产品行为是对的**；
- 想重跑一遍？先问自己：**它的失败率是多少？**

评测这行的专业性，不在于你能写出多漂亮的断言，而在于**当红色出现时，你能不能在 10 分钟内告诉团队：这是谁的错。**
