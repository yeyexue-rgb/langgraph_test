**深夜 CI 红了。你面前是一条失败的用例，只有一个冷冰冰的错误码。**

你有 30 秒决定：这是**提 bug 给开发**，还是**改自己的评测**？

赌错的代价是双向的——"其实是评测问题"你却提了 bug，开发被你骚扰三次后，再也不信你的红色；"其实是真缺陷"你却改了断言，缺陷漏到线上，你背锅。

这就是**假阴性**的可怕：评测系统自己骗了自己，你还在报告上盖了绿色的章。

**【图 A：三种「红」的分诊决策树】**

老手和新手的区别，在于**先分诊**。红其实有三种：

| 类型 | 特征 | 处置 |
|---|---|---|
| ① 逻辑缺陷 | 稳定复现，证据指向代码 | 提 bug，修产品 |
| ② 假阴性 | 产品行为其实是对的 | 修评测，别动产品 |
| ③ 抖动型不稳定 | 概率性、时好时坏 | 容错 + 可观测 |

**它们的处置完全相反，但长得一模一样。** 所以你需要一套方法去"逼问"它——我管它叫**三角定位法**：① 证据链完整吗（看现场，不看错误码）；② 能稳定复现吗（最小复现，连跑 3 次）；③ 换维度也错吗（规则断言 ↔ LLM 指标交叉验证）。

**【图 B：一次排查的现场证据】**

讲我的真实案例。多 Agent 架构下，SQL 用例**时好时坏，2/3 失败**，报 `INVALID_SUBAGENT_RESULT`。而单 Agent 模式下同一条用例 5 次全绿——**光这一点就排除了数据库问题**。

缩小范围（单独构建 SQL 子 Agent 连跑 3 次）：2 次失败、1 次成功。既不是稳定失败（排除逻辑缺陷），也不是稳定通过（排除假阴性）——**是抖动。**

但"抖"在哪？我抓了子 Agent 的原始 state：失败时，最后一条是**一条空的 AI 消息（`tool_calls=None`）**。往前看——`ToolMessage | [(3,)]` 赫然在目：**数据是对的！**

真相是：模型老老实实查完了数据，**却忘了调用结构化输出工具 `SubagentResult` 就结束了对话**。子 Agent 的输出被强类型约束，主管接不到有效结果，只能回一句"子专家返回了无效结果"。

**所以：数据没错、SQL 没错、评测也没错——是模型在"收尾"这一步偶发漏了动作。**

这里有一个特别容易搞混的判断：**错误码难看 ≠ 评测错了；偶发 ≠ 假阴性。** 评测报的错误码是如实记录的，它没撒谎。这属于**抖动型缺陷**：正确率 < 100%，但不可稳定复现——最可怕的是它会伪装成"偶发失败"，被一句"重跑就好了"盖过去。

**【图 C：抖动治理 = 容错 + 可观测】**

那加一次重试（2/3 → 0/3）算不算"掩盖问题"？**取决于你有没有把重试"看见"。** 裸重试 = 掩盖；可观测重试 = 治理。正确做法是两条腿：**容错**（只对终态可判的失败重试一次，带上限、只重试只读操作）+ **可观测**（记录重试率、首次成功率，把重试率做成正式质量指标）。

> 一句话：**抖动的正确处置，不是"让它不失败"，而是"让它失败得看得见"。**

顺便给一个**对照案例（同项目）**：提示词放在 `prompts/*.md`，但加载器只认 `.txt`——Agent 根本没吃到提示词，**评测却照样全绿**。这才是典型的假阴性：产品不达标，评测自己瞎了。

区分它们的，从来不是"红不红"，而是**证据链**。

## 四、长版逐图正文（10 张贴图的展开文案）

**图1（封面）**
评测红了，到底谁错了？假阴性 vs 真缺陷，一次真实排查。核心三招：看证据、看复现、看维度。实测数据：2/3 失败 → 0/3。记住一句话：别信"谁"，信证据。

**图2（三种「红」）**
红不是一种红。① 逻辑缺陷：产品真错了，稳定复现；② 假阴性：产品行为其实正确，是断言/配置/类型写错；③ 抖动型不稳定：概率性时好时坏。三者处置完全相反，但长得一模一样——所以需要一套方法去逼问它。

**图3（假阴性的代价）**
为什么必须分清？判断"这是缺陷"但其实是评测问题 → 开发再也不信你的红色；判断"这是评测问题"但其实是真缺陷 → 缺陷漏到线上，你背锅。同项目的真实假阴性案例：提示词是 .md、加载器只认 .txt，Agent 没吃到提示词，评测却照样全绿。

**图4（三角定位法）**
三个问题逼出真相：① 证据链完整吗（打原始 state，看现场不看错误码）；② 能稳定复现吗（绕开框架单独调那个模块，连跑 3 次）；③ 换维度也错吗（规则断言 ↔ LLM 指标交叉验证，结论反转就先怀疑断言）。口诀：看证据 → 看复现 → 看维度。

**图5（案例现象）**
多 Agent 模式下 SQL 用例时好时坏，2/3 失败，报 INVALID_SUBAGENT_RESULT。对照：单 Agent 模式同一条用例 5 次全绿——同一个库、同一条 SQL、同一份种子数据。第一反应"数据库坏了"，一秒被排除。

**图6（最小复现）**
绕开评测框架，单独构建 SQL 子 Agent，连跑 3 次：2 次 error、1 次 success。结论：不是稳定失败（排除纯逻辑缺陷）、不是稳定通过（排除假阴性）——它是抖动型不稳定。

**图7（抓现场·核心证据）**
最关键的一步：看原始 state，别只看错误码。失败时的最后几条消息里，`ToolMessage | [(3,)]` 数据是对的，可最后一条是 `AIMessage | calls=None`——模型查完了数据，却忘了调用结构化输出工具 SubagentResult 就结束了。

**图8（定性）**
偶发 ≠ 假阴性，报错难看 ≠ 评测错了。评测没撒谎（子 Agent 确实没返回有效结果）；也不是逻辑错（没有哪一行代码写错，是概率问题）。正确定义：抖动型缺陷 = 正确率 < 100% 但不可稳定复现。它最可怕之处是伪装成"偶发失败"被忽略。

**图9（处置：重试算掩盖吗）**
裸重试 = 掩盖，可观测重试 = 治理。容错：只重试"终态可判"的失败，带上限、只重试只读操作，两次都失败就如实上报。可观测：记录重试率和首次成功率——首次成功率才是真实稳定性，重试只是兜底。让它失败得看得见，而不是让它不失败。

**图10（判据表 + CTA）**
速查：稳定复现+指向逻辑 → 真缺陷提 bug；单架构绿多架构挂 → 抖动，单独复现"交接点"；断言不过但人工看对 → 假阴性，查断言/类型/阈值；配置改了像没改 → 假阴性，先验证配置生效。完整源码 + 诊断脚本：后台回复「agent」。
