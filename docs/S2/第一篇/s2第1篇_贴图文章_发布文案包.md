## 五、正文 · 长版（图文消息用，每张图前配一段）

**引子**
> 第一季讲了"要测什么"（五维/轨迹/基准）；第二季讲"用什么测、怎么更省力"。开篇先解决一个最普遍的问题：把评测从 Excel 里救出来。

**[图 2] 你熟悉的场景**
> 老板要报告 → Excel 手搓 → 没留档、不可比、换人就变。**问题不在你，在方式**：手工作业做不了工业化的事。

**[图 3] 概念先分清**
> promptfoo = CLI 评测 + 红队（YAML 驱动，多模型对比、可视化、安全扫描）；DeepEval = "Pytest for LLMs"（指标即断言，融入 pytest/CI）。**怎么选**：快速起步/安全扫描用前者；要细粒度指标/已在 pytest 体系用后者；不冲突，可同时用。

**[图 4] promptfoo 五步**
> 初始化 → 写 YAML → 跑评测（eval/view）→ 红队（redteam run）→ 接 CI（官方 GitHub Action）。**你的产物**：一份 YAML + 评测报告 + 红队报告，没写业务脚本。

**[图 5] 看不到源码怎么办（重点）**
> 多数测试工程师拿不到源码——没关系，promptfoo 本来就是黑盒工具。三种接法：① HTTP Provider：YAML 里填 Agent 接口地址（零代码）；② Python Provider：写十来行 `call_api` 调接口；③ 只有页面没接口：脚本 + Playwright 抓回复兜底。轨迹看不到？先推动研发暴露，拿不到就只断言可观测项。

**[图 6] 三条断言**
> 客服场景直接抄：`contains`（关键事实必须出现）、`not-contains`（禁止编造物流状态）、`llm-rubric`（主观维度交裁判）。**断的是"事办没办成"，不是"话怎么说"**——第一季的教训。

**[图 7] DeepEval 四步**
> 装 → 写 LLMTestCase + 指标断言 → `deepeval test run` → **指标分两类别搞混**：规则类先用（确定、便宜），裁判类要校准（主观维度）。

**[图 8] 亮点：ToolCorrectness**
> 把 `expected_tools` / `tools_called` 写进用例——**"过程"也被纳入断言**。这正是第一季"结果对 ≠ 过程对"的工具化落地。

**[图 9] 你的工作流**
> 用例来源（线上采样/事故复现/对抗用例）→ 双工具评测 → CI 门禁（阈值卡合入）→ 报告与沉淀（周会 + Git 版本化）。**工具替你跑，判断留给你。**

**[图 10] 四个坑**
> 裁判不校准（分数虚高）、只测输出（漏过程）、评测集污染、CI 直连真模型烧钱。

**[图 11] 写在最后**
> 半小时，换来"可复现、可对比、可进 CI"。别人还在手搓脚本，你已经在工程化交付评测——**这就是测试工程师在新赛道的位置**。
