# 学 Agent 测试，其实是件很划算的事

> Agent 测试进阶实战（第二季）· 番外篇
> 一篇坦白，写给还在观望的测试同学

---

## 先说动机，不绕弯子

这篇文章不劝你"转型"，也不制造焦虑。我只想老老实实回答一个问题：

**一个测试工程师去学 Agent 测试，到底图什么？**

我自己的答案是三个字：**划算**。

额，好像是两个。不管了，就是干！

不是因为不学就会被淘汰（这种话听多了，人也麻了），而是因为——**这件事的投入产出比，在我见过的技能升级里算相当高的**。理由是：你为了测好一个 Agent，被迫要补的东西，**每一样都是通用的、长期值钱的**。

换句话说：**Agent 测试是"入口"，但你能从里面拿走的，远不止"怎么测 Agent"。**

下面是我学下来的真实感受，包括犹豫、收获，也包括哪些人其实不必凑这个热闹。

---

## 一、我一开始也犹豫过

坦白讲，刚接触时我有两个顾虑：

**顾虑一：会不会又是一套"很快就会过时"的工具？**
这些年我们见过太多东西：某个测试框架火两年，某个平台三年没人维护。学了半天，最后只留下"我好像学过"。

**顾虑二：这东西离我的日常太远了。**
我手上的系统还是那些接口、页面、数据库，Agent 看起来像是"大模型团队的事"。

现在回头看，第一个顾虑**半对**：具体的工具确实会变（今天的 promptfoo、DeepEval，三年后未必还是主角）。但第二个顾虑**完全错了**——因为 Agent 测试真正难的部分，**跟"大模型"关系没那么大**，它难在**工程、标准和证据**上。而这三样，恰恰是测试工程师最能积累、也最该积累的东西。

## 二、学的过程里，我实际补上了三样东西

### 发现一：它逼你把工程能力补齐

以前做业务测试，很多时候"会点工具"就够了：会写用例、会用平台、会提 bug。

但 Agent 测试不一样。你要：

- 写**能复现的 pytest 用例**（不是点点点，是代码）
- 把评测**接进 CI**（门禁、分层执行、成本控制）
- 读懂**别人的源码**（找不到问题在哪，就得进代码里找）
- 会**抓现场**（打印原始状态、做最小复现、定位是模型的锅还是代码的锅）

这些没有一样是"Agent 专属"的。它们就是**测试开发的基本功**——只不过学 Agent 测试这件事，用一种"不得不"的方式，把你推到了这条路上。

说白了：**Agent 测试是最自然的"测开化"借口。** 你想测好它，就必须变成能写代码的那个人。

### 发现二：它把你从"执行者"变成"定义标准的人"

这是我收获最大的部分。

传统测试里，标准往往是别人给的：需求这么写，接口这么定义，我照着验。你的价值体现在**执行得准不准、快不快**。

但 Agent 评测不一样——**没有现成的标准**。什么叫"这个回答是对的"？什么叫"这个过程合格"？阈值定 0.7 还是 0.8？哪些用例该用规则断言、哪些该上裁判？

**这些只能由你来定。** 而一旦你定了标准，你就从"执行者"挪到了"定义者"的位置上。

这个位移很关键。因为**工具会过时，标准不会**。三年后可能没人记得 promptfoo 是什么，但"怎么设计一套可复现的评测体系"这套思维方式，会一直跟着你。

**【图 B：从执行者到定义者】**

### 发现三：表达能力和文档能力，被顺带逼出来了

评测这件事有个天然属性：**你必须把"为什么"讲清楚**。

- 为什么要用两层断言？
- 为什么这条用例失败不算产品的锅？
- 裁判给 0.6 分，凭什么？

你没法用"我觉得"糊弄过去——因为评测本身就是在**建立可被检验的判断**。写这种文档的过程，就是在训练你把技术问题讲到别人能懂。

对测试工程师来说，这可能是最被低估的能力：**你越往上走，越是在做"让人相信你的判断"这件事。**

## 三、技能栈到底深了什么？

把话说具体一点，学 Agent 测试这几个月，我实际用到的这些能力，**没一样只能用在 Agent 上**：

| 你练到的东西 | 通用性 | 还能用在哪 |
|---|---|---|
| 接口/端到端自动化测试 | 极高 | 任何后端系统 |
| pytest 工程化（夹具、标记、分层） | 极高 | 所有自动化项目 |
| CI 门禁与质量卡点 | 极高 | 研发流程任何一个环节 |
| 读源码 + 调试定位 | 极高 | 提 bug 时的"含金量" |
| LLM 评测方法论（指标/裁判/校准） | 中高 | 所有 AI 相关产品 |
| 安全测试（注入/越权/数据泄露） | 高 | 安全专项、合规审计 |
| 可观测与留档（指标趋势、回归） | 高 | 稳定性治理、线上质量 |
| 统计与判据思维（阈值、一致性） | 高 | 任何需要"下判断"的场景 |

注意最上面那四行——**它们占了这张表的一半，而且全部是"极高通用性"**。

这就是我说"划算"的原因：你以为自己在学一个前沿方向，实际上你在**补一个测试工程师最扎实的底座**。前沿是赠品，底座才是主菜。

## 四、坦白说，哪些人不必勉强

真诚一点，这事不是人人都适合，也不是必须现在做：

- **只想安稳做业务测试、不打算碰代码**：那就不必勉强。勉强学只会痛苦，而且学完也用不上；
- **把"AI 测试"当成一个能速成的证书**：别浪费时间。这行的门槛是"能独立设计一套评测"，不是"会用几个工具"；
- **本职工作完全没接触面、也找不到试验田**：先别急着学，先想办法**把手上的一件事做出可演示的结果**（这个更重要）。
- **容易焦虑刷课的人**：你已经很焦虑了，再刷课只会更焦虑。**跑通一条用例**比看十小时视频有用。

顺便说一句最近的行情（我自己也去翻了翻，纯当参考）：岗位需求确实在结构性变化，但**"懂 AI"本身并不是最硬的溢价，最硬的还是工程能力**——有统计说大厂测开面试考察后端开发能力的比例超过七成 [^1](https://agent.csdn.net/6a5cc5b3662f9a54cb90d760.html)。这恰好又印证了上面那句话：**底座先立住，前沿慢慢补。**

## 五、怎么开始才不痛苦

我自己验证过的路子，成本很低：

**【图 C：四步低成本起步】**

1. **先找一个你手上的真项目**——不要另起炉灶造玩具。就测你熟悉的东西，最好有真实数据；
2. **跑通"一条"用例**——不是十条，是一条。输入、期望、证据、判定，四样齐了就算成功；
3. **把它接进一次真实流程**——哪怕只是加进你自己的本地脚本，让"每次改完都跑一遍"变成习惯；
4. **写一篇复盘**——把踩的坑写下来。写的过程你会发现，你以为懂的地方其实没懂。

四步下来，你手上会有：一个能跑的用例、一次真实的运行结果、一篇你的记录。
**这就是全部的开始，也是最难的部分。**

## 六、写在最后

回到开头的问题：学 Agent 测试图什么？

我的答案是——图它**顺便**。

顺便把工程能力补齐了，顺便把"定义标准"的能力练出来了，顺便把表达和文档写顺了，顺便把这个方向最前沿的东西摸了一遍。

**这就是"何乐而不为"。** 不是因为它吓人，而是因为它划算。

至于要不要转成"AI 测试工程师"——那是后话。**先学，学了不亏；至于转不转，那时候你自己会有答案。**
