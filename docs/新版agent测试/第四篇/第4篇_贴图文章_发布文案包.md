## 五、正文 · 长版（图文消息用，每张图前配一段）

**引子**
> 上篇讲了怎么建评测体系，这篇讲怎么把它接进工程流水线。先讲两个真实事故：一个全 Mock 跑绿六个月、上线翻车；一个全真实调用，CI 慢贵飘三毒俱全。答案不是二选一，而是分层。

**[图 2] 两个翻车现场**
> 全 Mock 的团队，测试是"空心"的：覆盖率漂亮，但工具分发、重试、状态累积、兜底路由这些真正出 Bug 的地方一行没测。全真实的团队，PR 每次都烧钱等 10 分钟，输出还会因硬件差异波动。两类失败，都要避免。

**[图 3] 四层总览**
> 单元层测纯代码（工具、解析、Schema），集成层测编排（用替身），E2E 层验目标，评测层管质量。划重点：大多数人只盯 E2E，但集成层才是 Bug 重灾区——因为那是纯代码，逻辑密度最高。

**[图 4] 单元层**
> Agent 里能被解耦的纯代码比你想的多：工具实现、参数校验、响应解析、Prompt 模板渲染。把它们全部下沉到单元层——不花钱、跑得快、定位准。先做扎实这层，集成层能少踩一半坑。

**[图 5] 集成层**
> 测的是"模型之外的 Agent 代码"：工具返回空值会不会重试？429 会不会退避？第 7 步状态超窗口怎么办？上下文有没有从工具 A 传到工具 B？这些全是纯编排 Bug，一个真实模型都不需要。

**[图 6] StubLLM**
> 用一个"按剧本回应"的假 LLM：预设第 N 轮返回什么工具调用。用例里让它第一次返回空结果、第二次重试、第三次给最终答复——断言输出正确、且中途确实重试了。确定性、可断言、零成本。

**[图 7] 录制回放**
> 写用例时用真实模型跑一遍，录下（请求→响应）；CI 里回放录像。三步：录制、回放、变更后重录。选择原则：纯逻辑/异常路径用 StubLLM；真实模型行为（口吻、格式、工具选择）用录像。真实调用只留每晚少量冒烟。

**[图 8] E2E 层**
> 传统 E2E 验路径，Agent E2E 验目标（Tests enforce journeys, Agents verify goals）。混合策略：核心旅程保留确定性脚本；目标型场景用 agent 探索；数据用非生产副本；数量控制在 10-20 个。Slack 跑了 200+ 工作流验证了这个结论。

**[图 9] CI 分层矩阵**
> 按触发时机分层：PR 跑单元+集成替身（<5 分钟、零成本）；合并跑关键路径回放；夜间跑 E2E+评测集并卡阈值；发布前全量+真实冒烟。算笔账：全真实约 $600/月，替身+夜间冒烟约 $30/月，反馈快 10 倍。

**[图 10] 四坑与行动**
> 四个坑：全 Mock 空心化、全真实又慢又飘、断言写死话术、替身过期不更新。本周四件事：盘出纯逻辑部分、写第一个 StubLLM 用例、给 3 条核心流程录第一盘、评测集挂夜间加阈值。
