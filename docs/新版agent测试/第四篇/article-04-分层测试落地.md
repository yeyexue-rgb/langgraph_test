 # 全绿 CI 也会上线翻车？Agent 分层测试落地指南

> **Agent 测试实战系列 · 第 4 篇**
> 阅读对象：测试工程师 / QA / SDET ｜ 预计阅读：13 分钟
> 本篇目标：把评测体系接进工程流水线——单元 → 集成 → E2E → CI，每一层给可落地的做法和代码
> 上篇回顾：从 0 搭建评测体系 Eval（评测集 / 评分三件套 / 跑批）

---

先看一个真实得让人后背发凉的故事。

有团队给 Agent 写了集成测试，全部把大模型 Mock 掉——返回一个固定的假响应。CI 一路绿灯，跑了六个月，全绿。

上线当天翻车了。排查发现：在第 8 步循环的第 6 步，Agent 处理畸形工具响应的逻辑有问题。而那个永远返回 "Agent response here" 的 Mock，**根本没碰到编排层**——工具分发、重试逻辑、状态累积、兜底路由，这些真正出 Bug 的地方，一行都没测过。

另一头是另一种翻车：CI 里直接调真实大模型 API。慢、贵、还不稳定——一个 20 场景的评测套件，每次运行烧 0.5-3 美元；一次 15 秒的 LLM 调用让 CI 反馈循环彻底不可用；哪怕是 temperature=0，硬件浮点差异也会让输出波动，今天通过的测试明天无改动就红了。

**全 Mock 是"隐形空洞"，全真实是"烧钱又飘"。** 好消息是还有第三条路——一套分层的测试架构，每一层捕获不同类别的失败，且不承担其他方案的成本。

## 一、先分清楚：四层各测什么

| 层级 | 测什么 | 用真实模型吗 | 跑在哪 | 速度/成本 |
|---|---|---|---|---|
| 单元层 | 工具函数、参数校验、解析器、Schema | 不用 | 每次提交 | 秒级 / 免费 |
| 集成层（编排） | 工具分发、重试、状态传递、兜底路由 | 用替身（StubLLM/录制） | 每次 PR | 分钟级 / 极低 |
| E2E 层 | 真实任务目标能不能达成 | 少量真实 | 每日构建 | 分钟-小时 / 中 |
| 评测层 | 任务成功率、五维质量（上篇） | 真实 | 每日 + 发布前 | 小时级 / 可控 |

一个常见误区：大多数人把精力全花在 E2E 上，而**集成层（编排层）才是 Bug 重灾区**——因为那里是纯代码，逻辑密度最高，也最容易被"全 Mock"掩盖。

## 二、单元层：最便宜、最容易，先把能拆的都拆掉

Agent 系统里，纯代码的部分比你想的多得多。这些都应该有传统单元测试：

- **工具实现**：`query_order(order_id)` 的参数校验、错误码映射、超时处理；
- **参数解析**：模型输出的 JSON → 工具入参的转换逻辑（畸形输入必须有用例）；
- **响应解析器**：工具返回值 → 给模型的上下文片段；
- **Prompt 模板渲染**：变量替换、缺失字段处理、注入转义；
- **状态机/编排骨架**：不依赖模型的分支判断。

**原则：能和模型解耦的，全部下沉到单元层。** 这一层不花钱、跑得快、定位准，先把它做扎实，集成层能少踩一半坑。

## 三、集成层（核心）：用替身测透编排层

这一层测的是"模型之外的 Agent 代码"。核心手法是**两种替身**，配套使用：

### 手法 1：StubLLM——脚本化的假大脑

不用真实模型，用一个"按剧本回应"的假 LLM：你预设第 N 轮该返回什么工具调用、什么内容。这样编排逻辑就变成确定性的、可断言的：

```python
class StubLLM:
    def __init__(self, script):        # script: 预设的响应序列
        self.script = script; self.i = 0
    def respond(self, messages, tools):
        r = self.script[self.i]; self.i += 1
        return r                       # 例如：调用 query_order 工具

# 用例：第2轮工具返回空结果，验证它是否会正确重试
stub = StubLLM([
    {"tool_call": "query_order", "args": {"id": "A123"}},
    {"tool_call": "query_order", "args": {"id": "A123"}},   # 期望：空结果后重试
    {"final": "未查询到该订单，请核对订单号"},
])
assert run_agent("查一下 A123", llm=stub) == "未查询到该订单，请核对订单号"
assert stub.i == 3                                          # 中途确实重试了
```

**能测出来什么？** 工具返回空值会不会重试、429 会不会退避、第 7 步状态超上下文窗口怎么办、上下文有没有从工具 A 正确传到工具 B——**全是纯编排 Bug，一个真实模型都不需要。**

### 手法 2：录制回放（VCR）——真模型的"录像带"

写用例时用真实模型跑一遍，把（请求→响应）录下来；之后 CI 里回放录像，不花一分钱、完全确定性：

1. **录制**：本地带 `VCR_RECORD=1` 跑测试，真实调用模型，落盘请求/响应；
2. **回放**：CI 里默认走录像，请求哈希命中就返回录好的响应；
3. **更新**：业务或 Prompt 变更后，重新录制（把录像文件一起提交评审）。

**两种替身怎么选？** 纯逻辑/异常路径 → StubLLM；真实模型行为（口吻、格式、工具选择倾向）→ 录制回放。

> 需要真实模型的地方只留一处：每晚跑少量"冒烟"用例，确认模型侧没有静默变更。
MDEOF
echo ok
**成本对照（给还在犹豫的你算笔账）：**

- **全真实方案**：20 个场景 × 每场景约 5 轮模型调用 ≈ 每次跑批 $1；按每天 20 次 PR 算，一个月约 $600，且每次 CI 多等 5-10 分钟；
- **替身 + 夜间冒烟**：PR 阶段零模型成本，夜间真实跑一次 ≈ $1/天 → 一个月约 $30；PR 反馈从 10 分钟压到 1 分钟以内；
- **结论**：把"贵且飘"的真实调用从每次提交挪到每天一次，**成本降 90%+，反馈快 10 倍**。这就是分层最直接的收益。

## 四、E2E 层：从"验路径"到"验目标"

传统 E2E 测的是一条固定旅程：点击 → 输入 → 断言。而 Agent 的执行路径是现场生成的——同一目标会走出不同的路。

Slack 工程团队用 Playwright 跑了 200+ 个 agentic E2E 工作流后，给了个精准的总结：

> **Tests enforce journeys. Agents verify goals.**（传统测试校验路径，智能体验证目标。）

所以 E2E 层的正确姿势是**混合**，而不是替代：

- **核心旅程用确定性脚本**（登录、下单主流程）——这些容不得"灵活"，必须路径固定、结果确定；
- **目标型场景用 agent 驱动探索**——给一句指令（"发一条线程消息"），让执行体重试、绕路、自适应，最终验证**目标是否达成**；
- **数据用非生产副本**——agent 探索会乱点乱试，绝不能碰生产数据；
- **数量可控**：核心旅程 + 10-20 个目标型场景，别贪多。

agentic E2E 的价值在于**探索性**：它能发现你写脚本时想不到的路径和边界。但它不能替代确定性测试——两者叠加，才是完整的 E2E 策略。

## 五、CI 落地：分层的执行矩阵

四层测试不能一锅端，按触发时机分层跑，兼顾反馈速度与成本：

| 触发时机 | 跑什么 | 时长预算 | 卡点策略 |
|---|---|---|---|
| 每次提交 / PR | 单元 + 集成（StubLLM/回放） | < 5 分钟 | 全绿才允许合并 |
| 合并到主干 | + 关键路径录制回放 | < 15 分钟 | 失败自动阻塞发布 |
| 每日夜间 | E2E 目标型 + 评测集（上篇） | < 2 小时 | 生成趋势报告 |
| 发布前 | 全量 + 少量真实模型冒烟 | 按需 | 失败禁止发版 |

**GitHub Actions 骨架（可直接抄）：**

```yaml
name: agent-ci
on: [pull_request, schedule]
jobs:
  fast:                      # 每个 PR：单元 + 集成（零模型调用）
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pytest tests/unit tests/integration   # StubLLM / 回放
  nightly:                   # 每晚：E2E + 评测集
    if: github.event_name == 'schedule'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python evals/run_eval.py --dataset evals/p0.jsonl
        env: { MODEL_API_KEY: ${{ secrets.MODEL_API_KEY }} }
      - run: python ci/check_threshold.py --min-success 0.90   # 阈值卡点
```

**三条纪律**：
1. **单元层必须 100% 绿**——纯代码还红着，别谈智能；
2. **集成层看成功率**——替身测试是确定性的，理论上应 100%；出现 flaky 说明编排有不稳定点，立即查；
3. **E2E flaky 处理**：自动重跑 2 次仍失败才判红，**但必须归档 flaky 记录**——跳过 = 放虎归山。

**附：集成层用例设计清单（直接抄）**

| 类别 | 用例示例 | 断言重点 |
|---|---|---|
| 正常路径 | 查订单 → 返回状态 | 调用序列 + 关键字段 |
| 空结果 | 工具返回空数组 | 是否重试 / 是否如实告知 |
| 报错重试 | 工具返回 429 / 500 | 退避策略、重试上限 |
| 畸形响应 | 工具返回非 JSON | 解析容错、降级话术 |
| 上下文传递 | A 的输出作为 B 的入参 | 参数是否完整传递 |
| 状态溢出 | 第 7 步累积超窗口 | 截断/摘要策略 |
| 兜底路由 | 连续失败 3 次 | 是否降级到人工/默认话术 |

> 这七类是编排层 Bug 的高发区，写完就能拦住大部分"上线才炸"的问题。

## 六、四个坑，每个都有人踩过

- **坑 1：全 Mock，测试空心化。** 覆盖率 90% 但编排层从未被测。对策：StubLLM 专门测试编排逻辑，别用假字符串糊弄；
- **坑 2：全真实，CI 又慢又飘。** 对策：真实调用只留夜间冒烟和发布前全量，PR 阶段一律替身；
- **坑 3：断言写死话术。** 集成层断言"调用序列 + 关键字段"，E2E 断言"目标达成条件"，绝不比对整句回复（五维框架第 2 篇的教训）；
- **坑 4：替身过期。** Stub/录像录完就不管，模型和 Prompt 变了还在测老行为。对策：替身文件进 Git、随业务变更同步更新、每晚冒烟守住真实模型变更。

## 七、本周就能做的 4 件事

1. 盘一遍你的 Agent 代码，把**纯逻辑部分**（工具、解析、编排）列出来；
2. 给编排层写第一个 StubLLM 用例（拿"工具返回空值"开刀）；
3. 给 3 条核心流程录第一盘"录像"，接进 PR 流水线；
4. 把上篇的评测集挂到 nightly，加上成功率阈值卡点。

做完这 4 步，你的 Agent 流水线就从"全绿也可能翻车"变成"红灯一定拦住"。

## 写在最后

回到开头的故事：那个全绿六个月、上线即翻车的团队，问题从来不是"测试不够多"，而是**测试都跑在了空气上**。

分层测试的本质，是让每一类 Bug 都在最便宜、最快的那一层被抓住：纯代码的归单元，编排的归替身，目标的归 E2E，质量的归评测集。**能 Mock 的精确 Mock，不能 Mock 的精准真跑。**
