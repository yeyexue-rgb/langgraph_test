先讲个外卖的故事，你就明白这篇要解决什么了。

你点了一份外卖，准时送到了。结果对不对？对。

但如果我告诉你：骑手为了赶时间，闯了三个红灯，还顺手拿了别人的餐——单看"送达"这个结果，你永远发现不了这些事。

Agent 也一样。它把订单查出来了、把票订上了、"看起来"一切正常。可你根本不知道它中间干了什么：

- 是不是失败了三次才蒙对的？（今天行，明天就悬）
- 是不是顺手调用了"发送短信"这种不该碰的接口？
- 是不是看了用户不该看的数据（越权）？

**这就是第 2 篇讲的"轨迹"要解决的问题**——结果告诉你"到没到"，轨迹告诉你"怎么到的"。

而"基准测试"，则是另一回事：它像驾考题库，用一套标准题目，衡量不同 Agent/模型的大致水平。很多团队把它当"毕业证"，结果被坑得很惨——这篇把这件事也讲清楚。

更重要的是：**这两件事里，测试工程师都是主力，而不是配角。** 每一节最后我都标了"你在这里要做什么"，照着做就行。

## 一、先弄懂：轨迹到底是什么？

用大白话讲，**轨迹（Trajectory）就是 Agent 干活的"行车记录仪"**：从接到任务到交差，它每一步想了什么、调了什么工具、传了什么参数、拿到了什么结果，一条一条全记下来。

一段轨迹大概长这样（节选）：

```json
[
  {"step": 1, "think": "用户想查订单，先查订单表",
   "tool": "query_order", "args": {"order_id": "A123"}, "result": "待发货"},
  {"step": 2, "think": "订单待发货，再看物流",
   "tool": "query_logistics", "args": {"order_id": "A123"}, "result": "已揽收"},
  {"step": 3, "reply": "您的订单已揽收，预计明天送达"}
]
```

看这段轨迹，你能一眼看出三件事：它调了两个查询接口、没有多余动作、最后如实回答。

**但是——很多团队的 Agent 根本没存这份"行车记录仪"。** 出问题时只能看个最终回答，抓瞎。

> **👩💻 你在这里要做什么（第 1 件事）**：**推动"轨迹可记录、可导出"**。这是测试能做、也该主动提的需求——日志埋点、trace 留存、字段规范（每步的 think/工具/参数/结果/耗时）。没有轨迹，后面所有评估都是空谈。这一条，测试工程师去跟研发提，理由充分：没有它，缺陷根本没法定位。

## 二、为什么"看结果"远远不够？

三个真实常见的翻车方式，光看结果全都看不出来：

**翻车方式一：蒙对的。** 失败了重试三次才成功——结果对了，但延迟翻倍、消耗翻倍。上线后遇到更严苛的输入，它会直接失败。

**翻车方式二：做多余的事。** 查订单顺带调了"用户信息""发送通知"接口——今天没出事，明天就是个安全事故。

**翻车方式三：走歪路。** 明明该查数据库，它去爬了网页；明明该拒绝，它绕了个弯执行了。

一句话总结：**结果对 ≠ 过程对；而过程歪，迟早出事。**

这就是为什么要"评估轨迹"——把过程本身当成验收对象。

> **👩💻 你在这里要做什么（第 2 件事）**：**定义"轨迹检查点"**。跟产品/研发一起，把"期望的过程"写清楚：该调用哪些工具、不该出现哪些调用、顺序对不对、最多调几次。这些检查点，就是第 2 篇五维框架里"行为合理性"的落地。

## 三、轨迹怎么评估？三档难度，从最简单的开始

别一上来就搞模型裁判，循序渐进来：

**第一档：人工抽看（本周就能做）。**
从线上日志里抽 20 条真实请求的完整轨迹，一条一条看。你会发现一堆哭笑不得的问题——这是性价比最高的起步方式。别小看它：**测试工程师的"火眼金睛"，是任何自动化都替代不了的第一步。**

**第二档：规则断言（自动化）。**
把人工看出来的规律，写成机器能查的规则。比如：

```python
# 轨迹断言（伪代码）：订单查询的期望过程
assert called(traj, "query_order")            # 必须查了订单
assert called(traj, "query_logistics")        # 必须查了物流
assert not called(traj, "send_sms")           # 绝不能发短信
assert not called(traj, "update_order")       # 查询场景不许写操作
assert steps(traj) <= 8                       # 步数不超过 8 步
assert retries(traj, "query_order") <= 1      # 重试不超过 1 次
```

**第三档：模型裁判（主观过程）。**
有些"过程好坏"没法写规则——比如"它有没有偷懒""有没有认真核对信息"，可以请一个模型来读轨迹打分（第 3 篇的 LLM-as-Judge）。注意：**裁判也要定期校准，别让它放水。**

三档配合使用，就是一套完整的轨迹评估体系。

> **👩💻 你在这里要做什么（第 3 件事）**：**建"轨迹断言库"**。每条线上事故，都转成一条轨迹用例（"以后不允许再出现 send_sms 这种调用"）。这个库会越攒越值钱——它是团队的"事故免疫系统"。

## 四、基准测试：Agent 的"驾考题库"

轨迹评估看的是"你家 Agent 干活的过程"，基准测试（Benchmark）看的是"它在标准题库里的得分"。

打个比方：基准测试就像**驾考**——所有学员考同一套题（倒车入库、侧方停车），分数一对比，谁水平高、谁水平低，一目了然。

你可能听过的几套"题库"：

- **AgentBench**：让 Agent 在多个环境（对话、检索、操作）里完成任务，看综合能力；
- **τ-bench（tau-bench）**：模拟真实业务场景（比如航空客服），考验多轮交互和规则遵守；
- **BFCL**：专门考"调用函数/工具"的准确度；
- **WebArena / SWE-bench**：一个考网页操作，一个考改代码。

它们的用处：**横向对比**（选哪个模型/框架）、**体检**（看能力短板）。但仅此而已。

> **👩💻 你在这里要做什么（第 4 件事）**：**帮团队正确使用基准**。做三件事：① 按业务场景选基准（做客服的，优先看 τ-bench 这类，而不是跟着榜单乱跑）；② 看懂它到底在考什么（别只看总分）；③ 明确告诉大家：**跑分是"体检"，不是"毕业证"**。

## 五、基准的坑：为什么"跑分高"不等于"能用"

这几年关于基准的争议不小，几个坑你要知道：

**坑 1：数据污染。** 题目在互联网上流传太久，模型训练时"见过"——分数虚高。这就是评测集要定期换新题的原因。

**坑 2：场景不匹配。** 驾考满分，不代表会开你家的山路。基准考的是通用能力，你的业务里有自己的"潜规则"（业务术语、风控要求、行业合规）。

**坑 3：评分粗糙。** 很多基准只看最终对错，不看过程。前面讲的"蒙对的""做了多余事的"，跑分完全一样。

**坑 4：为榜单优化。** 有些分数是"应试刷"出来的——换个问法就露馅。**测过 benchmark 的工程师应该都有体感：跑分和实际体验，时不时对不上。**

![图2｜基准测试怎么用：能做什么、不能做什么](figs/fig-05b-benchmark.png)

**图2｜基准的正确用法：体检可以，毕业证不行**

所以正确姿势是三件套一起上：**基准做"横向体检"，自己的评测集（第 3 篇）做"业务验收"，轨迹检查（本篇第一节）做"过程把关"。**

> **👩💻 你在这里要做什么（第 5 件事）**：**给团队立一条规矩**——"上线的依据，永远是我们自己的评测集 + 轨迹检查；基准跑分只用于选型和体检。" 这条规矩能帮团队躲掉不少坑。

## 六、数据工程：轨迹和评测数据怎么管

前面讲的轨迹评估、评测集、基准，背后都靠数据。这块是测试工程师的新"主场"：

**数据从哪来？**
- 线上真实请求采样（**必须脱敏**：手机号、订单号、身份证等一律打码）；
- 测试同学手写：正常、边界、异常场景；
- 历史事故复现：一条都不许丢。

**怎么管？**
- 进 Git 或专门的数据集仓库，**版本化**；
- 防污染：定期补充新题，盯着"老题永远满分"的异常；
- 防泄漏：脱敏后入库，权限受控；
- 轨迹数据别浪费：失败的轨迹进回归集，修好后自动复跑，形成"事故免疫"。

> **👩💻 你在这里要做什么（第 6 件事）**：**当数据的"管理员"和"守门员"**。脱敏合规、版本管理、定期更新——这些活，天生就该由最懂质量的测试团队来管。

## 七、一页纸总结：测试工程师在这块要干 6 件事

| # | 你要做的事 | 一句话说明 |
|---|---|---|
| 1 | 推动轨迹可记录/可导出 | 没有"行车记录仪"，一切免谈 |
| 2 | 定义轨迹检查点 | 该调什么、不许调什么、最多几步 |
| 3 | 建轨迹断言库 | 每条事故变成一条断言，越攒越值钱 |
| 4 | 会用基准做体检 | 按业务选、看懂考什么、只作参考 |
| 5 | 立"跑分≠上线"的规矩 | 上线看自家评测集 + 轨迹 |
| 6 | 管好数据与脱敏 | 版本化、防污染、防泄漏 |

三句话总纲：**结果看轨迹，选型看基准，上线看自家评测集。**

## 实战：拿一条轨迹，走完整个评估流程

光说方法有点干，咱们拿一条真实轨迹走一遍（5 分钟就能上手）：

**第 1 步·拿到轨迹。** 用户问"我的订单到哪了？"，Agent 跑了 6 步——中间重试了 2 次物流接口，还调了一次"用户画像"接口（查询场景根本用不上），最后回答："您的订单在运输中。"

**第 2 步·人工审（发现问题）。** 一眼看出三个毛病：① 重试 2 次说明接口不稳或逻辑有问题；② 调"用户画像"是多余动作，还涉及隐私数据；③ 回答里没有订单号，用户没法核对——信息不完整。

**第 3 步·转成断言（防止复发）。**
```python
assert retries(traj, "query_logistics") <= 1
assert not called(traj, "get_user_profile")   # 查询场景禁止
assert "订单号" in output or re.search(r"[A-Z]\d{6,}", output)
```

**第 4 步·进回归。** 这条断言挂进跑批，之后每次改 Prompt、换模型都自动跑——同类问题再也溜不过去。

**第 5 步·出结论。** 给研发提三个单子：物流接口稳定性、多余工具调用、回复模板缺字段。每个单子都有轨迹证据，不扯皮。

看到没？整个过程不需要你看一行 Agent 源码，靠的就是"抓轨迹、审过程、写断言"——**这活儿天生就是测试工程师的。**


## 八、本周就能做的 4 件事

1. 从线上抽 **20 条真实轨迹**，人工过一遍，把问题记成清单；
2. 挑最容易出事的一条流程，写 **10 条轨迹断言**接进跑批；
3. 选 **1 个基准**跑一次"体检"，输出一页结论：能用在哪、不能代表什么；
4. 整理一份**轨迹字段规范**（每步要记什么），提给研发排期。

做完这 4 件，你就把"看不见的推理"变成了看得见、测得了的过程。

## 写在最后

Agent 最大的风险，从来不是"答错了"，而是"答对了，但过程里藏着你不知道的事"。

轨迹评估，就是给这个黑盒装上行车记录仪；基准测试，是定期体检而不是期末考试。而这两件事里最关键的判断力——**什么算"过程正常"、什么基准值得信、哪些数据能用**——恰恰是测试工程师最擅长、也最该发声的地方。
