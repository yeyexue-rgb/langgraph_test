## 五、正文 · 长版（图文消息用，每张图前配一段）

**引子**
> 上篇给了五维框架，有人问：五维很好，但总不能每条用例都人工判吧？对——所以这篇把它变成流水线。Eval 不玄乎：出卷、考试、判卷、出报告。20 条用例起步，本周就能让 Agent"持证上岗"。

**[图 2] 先承认：手动测试是"自嗨"**
> 你手动跑的那 10 个 case，题是你挑的、预期是你写的、路径是你能想到的。真实用户不按你的剧本走。而 benchmark 高分也不保险——Anthropic 直言见过太多 90% 基准分的团队生产翻车。解法只有一个：建一套你业务自己的 Eval。

**[图 3] Eval 的最小闭环**
> 输入场景 → 让 Agent 执行 → 自动评分 → 输出结论。第 2 篇的五维框架是"评分标准"，Eval 就是"批量自动执行评分标准的流水线"。有了它，改 Prompt、换模型、调工具，跑一遍就知道有没有改坏——这就是 Agent 的回归测试。

**[图 4] Step 1 · 盘点场景**
> 别急着写代码。列场景、按五维列风险点、按"用户量 × 翻车后果"排优先级。先保证 P0 场景测深，而不是所有场景测浅。盘完你会发现：要测的东西其实没那么多。

**[图 5] Step 2 · 建评测集**
> 评测集是地基，但别想着一口气搞 1000 条。20 条起步：线上真实日志采样最优先，再补手写用例和历史事故复现。格式用 JSONL，一行一条，进 Git 管理。注意：预期写"检查点"，别写死话术。

**[图 6] Step 3 · 评分三件套**
> 检查点用硬规则（字段、Schema、正则），能写规则绝不上模型；轨迹断言是 Agent 专属——比对期望的工具调用序列，抓"结果对、过程歪"；最后主观维度交给 LLM-as-Judge 兜底。

**[图 7] Judge 也要被管**
> 裁判模型偏懒、偏好长答案、自己还会漂移。对策：喂结构化模板（角色+维度+JSON 输出）、5 分制强制 reason、准备 50 条人工标注校准集，Judge 准确率低于 90% 就排查。

**[图 8] Step 4 · 跑批出报告**
> 50 行脚本跑通闭环：逐条执行 → 记录轨迹 → 判分 → 聚合。纪律：每条用例至少跑 3 遍（建议 5-10），报告看三个数——任务成功率、分维度通过率、稳定性方差。失败用例的轨迹存档，就是修 Bug 的第一手材料。

**[图 9] Step 5 · 接进流水线**
> 改 Prompt、换模型、改工具定义——这三个节点必须自动跑评测。成功率低于基线（如 90%）直接拦合入，分维度也要设下限。再记住四个前辈用事故换来的坑：评测集污染、只测成功率、Judge 裸奔、用例不更新。

**[图 10] 本周 5 件事**
> 拉日志挑 20 条 → 写 JSONL 进 Git → 按五维写检查点 → 写 50 行跑批脚本 → 补事故用例并把报告贴进周会。做完这 5 步，你就有了全组第一套能自动运行的 Agent 评测体系。
